# 推进

一页就够的工作交接工具。比如前后端联调：前端做完写好说明交给后端，后端接手；后端做完交给测试，测试接手；最后完成。每一步谁交给谁、说了什么，都留在待办上。

它要解决的问题是：工作交接时，消息发出去没人确认，事情就悄悄掉了。所以对方点“接手”之前，事情还算在原来的人手上。

这是 FDE 面试现场需求的补充实现，在面试结束后完成，不是现场做出来的。

**在线演示（不用注册）：<https://jaxson-zip.github.io/work-tracker/>**

第一次打开要下载约 5MB 的内存数据库，托管在 GitHub Pages 上，通常几秒，网络不稳定时可能要等几分钟。打不开的话，可以按下面的“本地运行”启动。

## 本地运行

不需要任何账号或密钥：

```bash
npm install
npm run demo
```

打开 <http://127.0.0.1:5174>，右上角可以切换三个身份：林晓（管理者）、陈晨、周宁。演示跑在浏览器里：真实的数据库迁移在内存版 PGlite 上执行，不连接外部服务，也不发真实消息（每一步会在右下角显示要发到群里的内容），刷新后恢复初始数据。

`npm run build:demo` 会把它构建成静态网站（`dist-demo/`），放到任何静态托管上都能打开。

## 需求和拆解

需求是面试现场口头提的，下面是我事后按记忆整理的：

> 做一个待办事项的最小 MVP：记录日常事务、生成待办，记下自己的关键事项不遗漏；支持任务流转，比如张三的工作交接给另一个人；接入飞书或企业微信的 Webhook。

我拆成了五块，按这个顺序做：

1. **数据和权限**：团队、成员、待办、流转记录；谁能看到什么、谁能操作什么。
2. **流转规则**：交出、接手、退回、撤回、完成，每一步都留记录。
3. **通知**：业务提交后才发群消息，失败重试。
4. **页面**：一页完成写待办、收待办、看流转。
5. **验证**：数据库测试覆盖规则和权限，浏览器测试走完整交接。

| 需求 | 怎么做的 |
| --- | --- |
| 记录事务、生成待办 | 合成一步：写一句话就是一条待办，日期自动识别（“周五前联调订单接口”），识别错了可以不要 |
| 关键事项不漏 | 等我接手的排在最前；逾期和今天到期有标记；每天早上发一份摘要 |
| 任务流转到另一个人 | 交给具体的人并写交接说明；对方接手前，事情还算在原来的人手上 |
| 接收方要确认 | 对方必须点“接手”或“退回”；退回必须写原因，事情回到原来的人手上 |
| 看到流转过程 | 经手的人能看到完整经过；管理者能看全队，以及每个交接已经等了多久 |
| 飞书或企业微信 Webhook | 两个通道都写了，每一步发到群里。企业微信会按手机号 @ 相关的人，飞书目前只发消息、不 @。在线演示不真发，但每一步会显示要发的内容（见“验证情况”） |

## 怎么用

页面只有一页：

- **左边写待办**：一句话写下，默认自己做，也可以直接交给别人。
- **左边收待办**：等我接手（接手或退回）、我手上的、我交出去的（看走到谁手上了）。
- **右边看流转**：点哪条就看哪条。谁写的、谁交来的、交接链（林晓 → 陈晨 → 周宁）、每一步的时间和交接说明；做完交给下一位或到此结束，也都在这里。

谁能看到什么：

- 经手过的人（写的、交出去的、接手的）能看到这条待办的完整流转。
- 团队管理者多一个“全队”视图：先看交接中等人接手的，再按人看各自手上的，也能点开看经过。别人手上的事默认只看；成员要离开时，可以代为交接。

## 设计取舍

- **所有业务写入和读取走一个数据库函数 `wt_command`**：权限、流转、经过记录和通知入队在同一个事务里，浏览器不能直接读写任何表。
- **通知用发件箱（outbox）**：业务提交成功后才发送，失败按退避时间重试，最多 5 次。发送语义是至少一次，极端情况下（对方已收到但响应超时）可能重复。
- **并发用版本号**：两个人同时操作同一条待办，后到的人会看到“别人刚改过”，不会悄悄覆盖。
- **手机号单独存放**：只用于企业微信群消息 @，同事看不到。
- **不用每分钟的定时任务**：页面操作后立即触发发送，每天的 Cron 负责生成摘要并补发，免费部署也能跑。

为了保持简单，这些有意没做：评论、验收、部门、一个人加入多个团队。

## 验证情况

```bash
npm test        # 单元和数据库测试，SQL 在 PGlite 里真实执行，Webhook 用假的 fetch
npm run e2e     # 构建演示版，用本机 Chrome 或 Edge 走完整交接：写待办、交接、退回、接手、完成、权限、修改、手机宽度
npm run build   # 类型检查和正式构建
```

**已验证**：流转规则、权限、版本冲突和通知队列（数据库测试）；完整交接流程（浏览器测试，测的就是演示版的构建产物）；通知的请求格式和重试（用假的 fetch）。演示里显示的群消息，就是数据库入队、真实发送时读取的同一份内容（真实发送时，企业微信 @ 的是手机号，并在末尾附上系统链接）。

**还没有验证**：

- 真实的 Supabase 项目和 Vercel 部署。下面的部署步骤还没有实际走过。
- 真实的企业微信和飞书群。这个版本的通知代码还没有发到过真实群里，测试也都不会访问真实的群机器人。

## 部署（Vercel + Supabase）

1. 新建 Supabase 项目，按文件名顺序执行 `supabase/migrations/` 下的 SQL。
2. 新建 Vercel 项目并导入仓库，按 `.env.example` 配置环境变量。
3. 登录网站创建团队，在 Supabase 里查到团队 ID（`select id, name from wt_workspaces`），和群机器人地址一起写入 `WORKSPACE_WEBHOOKS`，然后重新部署。
4. 点页面顶部的团队名生成邀请码发给同事；每个人在同一处填手机号，企业微信群消息才能 @ 到本人。

每日摘要由 `vercel.json` 里的 Cron 在北京时间 09:05 触发。

## 复用说明

这个项目基于我之前的个人待办项目 `to_do`，以及在它之上做的团队版 `work-tracker` 改造：

- **复用 `to_do`**：中文日期解析，Supabase 和 Vercel 的工程结构。
- **复用 `work-tracker`**：团队和邀请的数据模型，通知队列和飞书签名。
- **移除**：个人待办、微信 / 飞书机器人、事务记录、验收等，它们会让工具变复杂。
- **新写**：接手确认的交接流程、按经手人的可见范围、企业微信通道、每日摘要、单页界面、浏览器里运行的演示版。

开发过程使用了 AI 辅助（Claude Code），设计决策和验收由我负责。
