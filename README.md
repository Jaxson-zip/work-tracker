# 推进

团队的关键事项流转工具：记下事务，生成待办，转交给具体的人并由对方确认接收，通知发到企业微信或飞书群。

它要解决的问题是：工作在人和部门之间交接时，发出去的消息没人确认，事情就悄悄掉了。所以这里的转交在对方点“接收”之前不算完成，事项仍然算在原负责人名下。

## 本地运行

不需要任何账号或密钥：

```bash
npm install
npm run demo
```

打开 <http://127.0.0.1:5174>，在左下角切换林晓、陈晨、周宁三个身份。演示使用真实的 SQL 逻辑（内嵌 PGlite），不连接外部服务，也不发真实消息。

## 功能

| 需求 | 做法 |
| --- | --- |
| 日常事务记录 | “事务记录”页一行记下，可标记为关键 |
| 生成待办 | 一句话创建，自动识别文字里的日期（“周五跟进合同”）；记录也能一键生成待办 |
| 知道先做什么 | “我的事项”按 等我接收 → 被退回 → 等我验收 → 已逾期 → 今天 → 受阻 → 之后 分组 |
| 任务流转 | 待开始 → 进行中 → 受阻 / 待验收 → 已完成，也可取消；受阻、退回、取消都要写原因 |
| 负责人转交 | 按部门选人；对方可以接收或退回，发起人在接收前可以撤回 |
| 整体交接 | 休假、离职时把一个人的未完成事项一次转出，接收方可以全部接收 |
| 按部门看 | “全部事项”按部门筛选，看谁在做、卡在哪 |
| 企业微信 / 飞书通知 | 转交、接收、退回、验收、受阻实时发到群并 @ 相关的人；每天早上发待办摘要 |
| 飞书记事（可选） | 私聊机器人发“记录 …”“待办 …”就能记下 |

## 设计取舍

- **所有业务写入走一个数据库函数 `wt_command`**：权限判断、状态流转、操作历史和通知入队在同一个事务里，前端绕不过去。
- **通知用发件箱（outbox）**：业务提交成功后才发送，失败按退避时间重试，最多 5 次，页面上可以手动重发。发送语义是至少一次，极端情况下（对方已收到但响应超时）可能重复。
- **并发用版本号**：两个人同时操作同一件事，后到的人会看到“别人刚改过”，不会悄悄覆盖。
- **手机号单独存放**：只用于群消息 @，同事看不到别人的手机号。
- **不用每分钟的定时任务**：页面操作后立即触发发送，每天的 Cron 负责生成摘要并补发，免费部署也能跑。

## 部署（Vercel + Supabase）

1. 新建 Supabase 项目，按文件名顺序执行 `supabase/migrations/` 下的 SQL。
2. 新建 Vercel 项目并导入仓库，按 `.env.example` 配置环境变量。
3. 登录网站创建团队，在 Supabase 里查到团队 ID（`select id, name from wt_workspaces`），和群机器人地址一起写入 `WORKSPACE_WEBHOOKS`，然后重新部署。
4. 每位成员在“成员”页填手机号，群消息才能 @ 到本人。

每日摘要由 `vercel.json` 里的 Cron 在北京时间 09:05 触发。飞书机器人的配置见 [docs/feishu-setup.md](docs/feishu-setup.md)。

## 复用说明

这个项目基于我之前的个人待办项目 `to_do`，以及在它之上做的团队版 `work-tracker` 改造：

- **复用 `to_do`**：中文日期解析，Supabase 和 Vercel 的工程结构。
- **复用 `work-tracker`**：团队、邀请和权限的数据模型，通知队列，飞书回调验签和命令解析。
- **移除**：个人待办界面、微信 / OpenClaw 机器人和离线存储，它们和这个需求无关。
- **新写**：接收确认的转交流程、部门、取消、企业微信通道、每日摘要、整套界面。

接收确认和企业微信通道的设计，来自这道题最初的 MVP。开发过程使用了 AI 辅助（Claude Code），设计决策和验收由我负责。
