# 推进

一页就够的工作交接工具。比如前后端联调：前端做完写好说明交给后端，后端接手；后端做完交给测试，测试接手；最后完成。每一步谁交给谁、说了什么，都留在待办上。

它要解决的问题是：工作交接时，消息发出去没人确认，事情就悄悄掉了。所以对方点“接手”之前，事情还算在原来的人手上。

## 本地运行

不需要任何账号或密钥：

```bash
npm install
npm run demo
```

打开 <http://127.0.0.1:5174>，右上角可以切换三个身份：林晓（前端，管理者）、陈晨（后端）、周宁（测试）。演示使用真实的 SQL 逻辑（内嵌 PGlite），不连接外部服务，也不发真实消息。

## 怎么用

页面只有一页：

- **上面写待办**：一句话写下，日期自动识别（“周五前联调订单接口”）；默认自己做，也可以直接交给别人。
- **下面收待办**：等我接手（接手或退回）、我的待办（完成或交给下一位）、我交出去的（看走到谁手上了）。
- **点开看流转**：谁写的、谁交来的、交接链（林晓 → 陈晨 → 周宁）、每一步的时间和交接说明。

谁能看到什么：

- 经手过的人（写的、交出去的、接手的）能看到这条待办的完整流转。
- 团队管理者多一个“全队”视图，能看到所有待办走到了谁手上，也能点开看经过。

每一步都会发到企业微信或飞书群，并 @ 相关的人；每天早上发一份摘要（待接手、已逾期、今天到期）。

## 设计取舍

- **所有业务写入和读取走一个数据库函数 `wt_command`**：权限、流转、经过记录和通知入队在同一个事务里，浏览器不能直接读写任何表。
- **通知用发件箱（outbox）**：业务提交成功后才发送，失败按退避时间重试，最多 5 次。发送语义是至少一次，极端情况下（对方已收到但响应超时）可能重复。
- **并发用版本号**：两个人同时操作同一条待办，后到的人会看到“别人刚改过”，不会悄悄覆盖。
- **手机号单独存放**：只用于群消息 @，同事看不到。
- **不用每分钟的定时任务**：页面操作后立即触发发送，每天的 Cron 负责生成摘要并补发，免费部署也能跑。

为了保持简单，这些有意没做：编辑待办内容（写错了可以删掉重写，流转过的不能删）、评论、验收、部门、一个人加入多个团队。

## 部署（Vercel + Supabase）

1. 新建 Supabase 项目，按文件名顺序执行 `supabase/migrations/` 下的 SQL。
2. 新建 Vercel 项目并导入仓库，按 `.env.example` 配置环境变量。
3. 登录网站创建团队，在 Supabase 里查到团队 ID（`select id, name from wt_workspaces`），和群机器人地址一起写入 `WORKSPACE_WEBHOOKS`，然后重新部署。
4. 点页面顶部的团队名生成邀请码发给同事；每个人在同一处填手机号，群消息才能 @ 到本人。

每日摘要由 `vercel.json` 里的 Cron 在北京时间 09:05 触发。

## 测试

```bash
npm test        # 单元和数据库测试，SQL 在 PGlite 里真实执行，Webhook 用假的 fetch
npm run e2e     # 用本机 Chrome 或 Edge 走完整交接：写待办、交接、退回、接手、完成、权限、并发冲突、手机宽度
npm run build   # 类型检查和构建
```

测试都不会访问真实的群机器人。

## 复用说明

这个项目基于我之前的个人待办项目 `to_do`，以及在它之上做的团队版 `work-tracker` 改造：

- **复用 `to_do`**：中文日期解析，Supabase 和 Vercel 的工程结构。
- **复用 `work-tracker`**：团队和邀请的数据模型，通知队列和飞书签名。
- **移除**：个人待办、微信 / 飞书机器人、事务记录、验收等，它们会让工具变复杂。
- **新写**：接手确认的交接流程、按经手人的可见范围、企业微信通道、每日摘要、单页界面。

开发过程使用了 AI 辅助（Claude Code），设计决策和验收由我负责。
