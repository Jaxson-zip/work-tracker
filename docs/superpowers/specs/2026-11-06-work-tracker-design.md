## 方案选择
1. 推荐：复用 React/Vite 与 Supabase Auth，增加团队领域及数据库事务/RLS；飞书连接服务端。保留现有个人工作区，增加团队工作台。
2. 飞书多维表格作为主库：减少录入建设，但权限与流转规则依赖飞书配置，现有同步逻辑不能直接复用。
3. 全新本地服务：无需云数据库，但需要替换身份、持久化和部署底座，复用收益较低。
采用方案 1；不自建密码认证或把前端身份选择当成安全边界。

## 用户路径
1. 注册/登录；创建团队并成为所有者，通过邀请凭证加入团队。角色为 owner/admin/member。所有者不可被误删，只有管理员能邀请和管理普通成员。
2. 手动记录事务：标题、正文、发生日期、重要性；记录可以保持纯记录，或转为关联待办，避免重复转换。
3. 待办必须有有效负责人；截止时间可选，关键事项建议填写。记录下一步动作与下次跟进日期。
4. 流转：待接单 -> 进行中 -> 待验收 -> 已完成；阻塞可标记原因，管理员/创建者验收或退回，转交必须选有效成员并填写原因。所有动作保留操作者、时间与变更。
5. 我的关键事项展示本人负责、本人创建待验收、到期/逾期、跟进到期和阻塞事项；提供团队全量清单和详情日志。
6. 飞书：网页手动录入为基础；可配置事件回调，把授权绑定成员的文本消息记为事务或任务；配置自定义机器人 webhook 后，在指派/转交/待验收等事件及到期扫描时发送通知。没有凭据时明确显示未连接。

## 实现边界
- 原个人功能与团队数据分开，保留原功能模块；修复本地缓存按账号区分、退出/切换后旧响应污染。
- 新增团队、成员、邀请、事务记录、任务、任务活动及通知队列表；独立表名，不破坏原 memo_items。
- 任务状态变化、权限判断、活动记录和通知入队由数据库事务统一执行，前端不直接越权写入。
- 读取通过 Supabase RLS 限制为有效成员；负责人必须属于同一团队；乐观版本号拒绝覆盖并发更新。
- 飞书密钥仅在服务端；回调按官方文档验证，重复事件去重，外部身份显式绑定。通知失败可重试，界面不虚报成功。
- 不复制 .env、.git、.vercel、node_modules 或构建缓存；新项目使用独立缓存键，不能自动接管原应用数据。
